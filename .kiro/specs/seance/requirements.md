# Requirements Document

## Introduction

Séance is presence check-in for Screech. A host runs a séance from a laptop. Everyone in the room checks in by hearing it: the laptop repeatedly screeches a `checkin` Packet, each attendee's phone decodes it on the normal Listen_Screen, and the attendee taps Join. No QR code and no typed code is needed. The host screen is a big room display where an unlit candle lights for each person who checks in, and the host can download the attendance as a CSV file.

Séance reuses what already exists and adds no new protocol type:
- The `checkin` Packet type, the 140-byte `SIZE_CAP`, `encode()` and `decode()` already exist in `packages/core` (spec `screech-protocol`). Séance defines only the text carried in the `checkin` Body, as a pure build and parse pair in `packages/core`.
- The Awaken_Screen, Speak_Screen, Listen_Screen, Reveal_Screen, Hold_State_Machine, `unlockAudio`, `ensureRunning`, Transmit_Volume and Exorcise_Toggle come from spec `spirit-box-app`. Séance extends them and does not replace them.
- The rule that no UI_Sound plays on the Listen_Screen comes from spec `haunting-sounds`.
- The visual reference is `docs/design/Seance.dc.html`, together with the rules of the ui-theme steering.

Séance is the first user of `apps/checkin-api`. The server stack is decided: Netlify Functions in TypeScript under `/api`, with data in Netlify Blobs, on the same domain as the web app.

Séance amends two rules of `spirit-box-app`. First, 13.6 shows the full decoded text of a `checkin` Packet in the Action_Card. For a `checkin` Packet that parses, this spec replaces that behaviour with the Join_Screen. Second, the Listen_Screen stops capture whenever it shows a result. The Join_Screen follows the same rule, and a Packet that does not parse keeps the behaviour of 13.6.

### Assumptions

The brief leaves the following open. These requirements resolve each point, and the design phase may refine them.

1. **Session_ID form.** The Session_ID is 8 characters from the Hunt_Alphabet of spec `ghost-hunt` (31 characters, no `0`, `O`, `1`, `I`, `L`), generated by the server from a cryptographically secure random source.
2. **Host_Secret form.** The Host_Secret is 32 random bytes from a cryptographically secure random source, encoded as 43 base64url characters.
3. **Window and Rolling_Code.** The Window_Number is `floor(unixSeconds / 30)`. The Rolling_Code is the first 6 decimal digits of the HMAC-SHA-256 of the decimal text of the Window_Number, keyed with the Host_Secret bytes, read as a 31-bit big-endian integer modulo 1,000,000 and left-padded with zeros (dynamic truncation as in RFC 4226).
4. **Server holds the secret.** The server must recompute the Rolling_Code, so it stores the Host_Secret. The Host_Secret is stored only in the Blobs record of the session, and never in a response other than the creation response.
5. **Clock skew.** The browser of the host and the server may disagree on the time. The host browser gets the time offset from the `Date` header of the creation response and applies it, so that the Rolling_Code in the Packet matches the server's Window_Number. Accepting the previous Window covers the delay between a screech starting and an attendee tapping Join.
6. **Packet text.** The `checkin` Body text has the exact form `S1:<Session_ID>:<Rolling_Code>`. It is about 20 bytes, so a screech is short. The title is not in the Packet. The Join_Screen gets the title from the server.
7. **Repeat check-in.** A second check-in from the same Device_ID does not change the stored name or time. The server answers with the original record and a flag that says the device was already checked in.
8. **Order of checks.** The server checks, in this order: the session exists, the session is open, the body is valid, the Rolling_Code is valid, and then it records the check-in. A repeat check-in from a known Device_ID is answered with success even when the Rolling_Code has expired, as long as the session exists. This keeps the "same screen again" behaviour after the session has ended.
9. **Names are not unique.** Two attendees may use the same name. Each gets a candle.
10. **Candle capacity.** The Candle_Circle is designed for up to 100 candles. Beyond 100 check-ins the count and the CSV stay correct, and the extra names are shown in a scrolling list below the circle.
11. **Abuse.** v1 has no accounts and no rate limit beyond the one check-in per Device_ID. A person who hears the screech can check in more than once with several Device_IDs. This is accepted for a room-trust event tool and is not solved in v1.
12. **Tampering.** The server answers a wrong or missing Host_Secret with the same error for a missing session, so that a caller cannot find out which Session_IDs exist from the host endpoints.
13. **Host secret in the page.** The Host_Secret lives in React state and in `sessionStorage`. Reloading the host tab keeps the séance. Closing the tab loses the Host_Secret, so the host can no longer end the séance or download the attendance, and the séance expires after 24 hours. The host page says this in plain words.
14. **Screech repeat interval.** The interval is measured from the start of one screech to the start of the next. A random value from 10 to 15 seconds is drawn for each interval. When the previous screech is still playing, the next one is delayed until it ends.
15. **Time format.** The server stores check-in times as UTC ISO 8601 text. The CSV carries that text. The host screen shows local time as `HH:MM`.

### Out of scope for v1

Sealed (encrypted) séances, multiple hosts, accounts, emails, a Ghost Hunt leaderboard, editing or removing a check-in, reopening an ended séance, per-IP rate limiting, and any other event data than a name and a time.

## Glossary

- **Spirit_Box_App**: The React web app in `apps/web`.
- **Core**: The `@screech/core` package.
- **Checkin_API**: The Netlify Functions in `apps/checkin-api`, served under `/api` on the same origin as the Spirit_Box_App.
- **Seance_Store**: The Netlify Blobs store that holds Sessions and Check_Ins.
- **Seance**: One check-in event: a Session_ID, a Title, a Host_Secret, an open or ended state, a creation time and a list of Check_Ins.
- **Session_ID**: A string of exactly 8 characters from the Hunt_Alphabet. It identifies one Seance.
- **Hunt_Alphabet**: The 31 characters `23456789ABCDEFGHJKMNPQRSTUVWXYZ`.
- **Title**: The text name of a Seance, 1 to 60 characters after trimming leading and trailing white space.
- **Host_Secret**: A random 32-byte secret, shown as 43 base64url characters, returned once when a Seance is created and sent by the host to the Checkin_API as `Authorization: Bearer <Host_Secret>`.
- **Open_Seance**: A Seance that has been created, has not been ended and is less than 24 hours old.
- **Ended_Seance**: A Seance that the host ended.
- **Expired_Seance**: A Seance that is 24 hours old or more. The Checkin_API treats an Expired_Seance as missing.
- **Window_Number**: `floor(unixSeconds / 30)`, an integer that identifies one 30-second Window.
- **Window**: A period of 30 seconds that starts at a multiple of 30 seconds of Unix time.
- **Rolling_Code**: The 6-digit decimal string that the Code_Function returns for a Host_Secret and a Window_Number.
- **Code_Function**: The pure function in Core `rollingCode(secret, windowNumber)` that computes the Rolling_Code with Web Crypto HMAC-SHA-256.
- **Code_Verifier**: The pure function in Core `verifyCode(secret, code, nowSeconds)` that returns true only when the code equals the Rolling_Code of the current Window or of the previous Window.
- **Checkin_Packet**: A Core Packet of type `checkin` produced by the Checkin_Builder, at most `SIZE_CAP` (140) bytes.
- **Checkin_Fields**: The two values Session_ID and Rolling_Code.
- **Checkin_Builder**: The pure function in Core that turns Checkin_Fields into the text `S1:<Session_ID>:<Rolling_Code>` and a Packet through Core `encode()`.
- **Checkin_Parser**: The pure function in Core that turns the text of a decoded `checkin` Payload back into Checkin_Fields, or into an error.
- **Device_ID**: A random identifier of 32 lowercase hexadecimal characters that the Spirit_Box_App creates once per browser and keeps in `localStorage`.
- **Check_In**: One record of a person at a Seance: a name, a Device_ID and a time.
- **Attendee_Name**: The name typed by an attendee, 1 to 32 characters after trimming leading and trailing white space, counted in Unicode code points.
- **Checkin_Log**: The pure data structure in Core that holds the Check_Ins of one Seance and adds a Check_In at most once per Device_ID.
- **Csv_Exporter**: The pure function in Core that turns a list of Check_Ins into CSV text.
- **Seance_Control**: The control on the Awaken_Screen and the Speak_Screen that opens the Host_Screen.
- **Host_Screen**: The laptop screen where the host starts, shows and ends a Seance.
- **Start_Form**: The part of the Host_Screen where the host types a Title and starts a Seance.
- **Room_Display**: The part of the Host_Screen shown while a Seance is open: the Title, the Candle_Circle, the Soul_Count and the Download_Button.
- **Candle_Circle**: A ring of candles on the Room_Display. A candle is unlit until a Check_In takes it, and then it is lit and shows the Attendee_Name under it.
- **Soul_Count**: The text "N souls present" on the Room_Display, or "1 soul present" when N is 1.
- **Download_Button**: The button "Download attendance (CSV)" on the Room_Display.
- **Screech_Loop**: The repeating sender on the Host_Screen that screeches a fresh Checkin_Packet through the existing transmit path every 10 to 15 seconds.
- **Poll_Loop**: The repeating request from the Host_Screen to `GET /api/seance/:id` every 2 seconds.
- **End_Hold**: The Hold_State_Machine control on the Room_Display that ends the Seance when held.
- **Join_Screen**: The screen on the attendee's phone, shown when the Listen_Screen decodes a Checkin_Packet that parses. It shows the Title and a name field.
- **Name_Field**: The text input on the Join_Screen for the Attendee_Name.
- **Join_Button**: The button "Join" on the Join_Screen.
- **Lit_Screen**: The screen "Your candle is lit" with a candle animation, shown after a successful check-in.
- **Candle_Animation**: The animation on the Lit_Screen in which a candle flame appears and flickers.
- **Exorcise_Toggle**: The control that turns all motion off, from spec `spirit-box-app`.
- **Listen_Screen**: Screen 4 of the Spirit_Box_App, from spec `spirit-box-app`.

## Requirements
### Requirement 1: Checkin Packet build and parse

**User Story:** As an attendee, I want my phone to understand the host's screech, so that I can join without typing a code.

#### Acceptance Criteria

1. WHEN the Checkin_Builder receives a Session_ID of exactly 8 Hunt_Alphabet characters and a Rolling_Code of exactly 6 decimal digits (characters 0 to 9), THE Checkin_Builder SHALL return the text `S1:<Session_ID>:<Rolling_Code>` (15 characters, 15 bytes) and a Checkin_Packet of type `checkin` that carries that text.
2. THE Checkin_Packet SHALL be at most 140 bytes (`SIZE_CAP`) in total, including the frame header, for every valid Checkin_Fields value.
3. WHEN the Checkin_Parser receives the text of a decoded `checkin` Payload in the exact form the Checkin_Builder produces, THE Checkin_Parser SHALL return the Session_ID and the Rolling_Code with every character unchanged, including leading zeros in the Rolling_Code.
4. FOR ALL valid Checkin_Fields, building a Checkin_Packet, decoding it with Core `decode()` and parsing the decoded text SHALL return Checkin_Fields equal to the original (round-trip property).
5. IF the text does not start with `S1:`, has a Session_ID that is not exactly 8 Hunt_Alphabet characters, has a Rolling_Code that is not exactly 6 decimal digits, has a missing `:` separator, or has any extra character (including leading or trailing whitespace, a trailing newline, or a trailing `:`), THEN THE Checkin_Parser SHALL return an error that names the first rule that failed, checked in this order: prefix, Session_ID, Rolling_Code, extra characters. THE Checkin_Parser SHALL return no Checkin_Fields in that case.
6. IF the Checkin_Builder receives a Session_ID that is not exactly 8 Hunt_Alphabet characters or a Rolling_Code that is not exactly 6 decimal digits (including empty, null, undefined, or non-string input), THEN THE Checkin_Builder SHALL return an error that names the first invalid field, and SHALL NOT return a Checkin_Packet or text.
7. FOR ALL strings, including the empty string and strings of at least 10,000 characters, THE Checkin_Parser SHALL return either Checkin_Fields or an error, and SHALL NOT throw an exception.

### Requirement 2: Rolling code

**User Story:** As a host, I want a code that changes every 30 seconds, so that a person who is not in the room cannot check in with an old code.

#### Acceptance Criteria

1. THE Code_Function SHALL return a Rolling_Code of exactly 6 decimal digits, including leading zeros, for every Host_Secret and every Window_Number that is an integer from 0 to 2^53 − 1.
2. FOR ALL Host_Secrets and Window_Numbers, calling the Code_Function twice with the same Host_Secret and the same Window_Number SHALL return the same Rolling_Code (determinism property).
3. FOR ALL generated Host_Secrets and Window_Numbers N, THE Code_Function SHALL return different Rolling_Codes for N and N+1 (neighbouring windows differ property). A 6-digit code collides with probability 1 in 1,000,000, so the design phase fixes the generator seeds or filters the rare colliding case.
4. THE Code_Function SHALL return the same Rolling_Code for every time from the start of a Window, inclusive, up to the start of the next Window, exclusive, where each Window is exactly 30 seconds long.
5. WHEN the Code_Verifier receives a code, a Host_Secret and a time in seconds, THE Code_Verifier SHALL return true if the code equals the Rolling_Code of the Window that contains the time.
6. WHEN the Code_Verifier receives a code, a Host_Secret and a time in seconds, THE Code_Verifier SHALL return true if the code equals the Rolling_Code of the Window immediately before the Window that contains the time.
7. IF the code equals only the Rolling_Code of a Window that is two or more Windows before the Window that contains the time, or of any Window after it, THEN THE Code_Verifier SHALL return false.
8. IF the code is not exactly 6 characters, each in the range "0" to "9", THEN THE Code_Verifier SHALL return false without throwing an error.
9. FOR ALL Host_Secrets and times, THE Code_Verifier SHALL return true for the Rolling_Code of the current Window and for the Rolling_Code of the previous Window, and SHALL return false for the Rolling_Code of the Window that is 2 Windows before and for the Rolling_Code of the next Window, when those codes differ from the two accepted codes (acceptance-set property).
10. THE Code_Function SHALL return the expected Rolling_Code for every test vector that the design phase derives from a reference HMAC-SHA-256 implementation, with at least 5 vectors that include a Window_Number of 0 and a Rolling_Code that begins with a leading zero.
11. IF the time received by the Code_Verifier is negative, not finite, or not a number, THEN THE Code_Verifier SHALL return false without throwing an error.

### Requirement 3: Check-in log and dedupe

**User Story:** As a host, I want each phone to count once, so that the Soul_Count equals the number of people in the room.

#### Acceptance Criteria

1. WHEN a Check_In with a Device_ID that is not yet in the Checkin_Log is added, THE Checkin_Log SHALL store the Check_In, increase its length by 1, and report that the Check_In is new.
2. WHEN a Check_In with a Device_ID that is already in the Checkin_Log is added, THE Checkin_Log SHALL keep the stored Check_In unchanged, leave its length unchanged, and return the stored Check_In with a report that the Check_In is a repeat.
3. FOR ALL sequences of 0 to 1,000 Check_Ins, THE Checkin_Log SHALL hold at most one Check_In per Device_ID, and its length SHALL equal the number of distinct Device_IDs in the sequence (invariant property).
4. FOR ALL sequences of 0 to 1,000 Check_Ins, adding the same sequence a second time SHALL leave the Checkin_Log unchanged, with every Check_In in the second pass reported as a repeat (idempotence property).
5. FOR ALL sequences of 0 to 1,000 Check_Ins, the stored name and time of each Device_ID SHALL equal those of the first Check_In with that Device_ID in the sequence, even when a later Check_In with the same Device_ID has a different name or an earlier time.
6. WHEN the Check_Ins of the Checkin_Log are requested, THE Checkin_Log SHALL return them in ascending order of time, with Check_Ins of equal time kept in the order they were added, and SHALL return an empty list if the Checkin_Log holds no Check_Ins.
7. WHEN the Soul_Count is requested, THE Checkin_Log SHALL return a value equal to its length, which is 0 if the Checkin_Log holds no Check_Ins.

### Requirement 4: CSV export

**User Story:** As a host, I want to download the attendance as a CSV file, so that I can open it in a spreadsheet.

#### Acceptance Criteria

1. THE Csv_Exporter SHALL return text whose first line is the header `name,checked_in_at`.
2. THE Csv_Exporter SHALL write one line for each Check_In, in the order of the Checkin_Log, with the Attendee_Name in the first field and the UTC ISO 8601 time in the second field, formatted as `YYYY-MM-DDTHH:mm:ss.sssZ`.
3. WHEN an Attendee_Name contains a comma, a double quote, a carriage return or a line feed, THE Csv_Exporter SHALL enclose the field in double quotes and replace each double quote inside the field with two double quotes.
4. THE Csv_Exporter SHALL separate lines with CRLF and SHALL NOT append a CRLF after the last line.
5. WHEN an Attendee_Name starts with `=`, `+`, `-`, `@`, a tab or a carriage return, THE Csv_Exporter SHALL put a single quote before the name so that a spreadsheet does not run the name as a formula, and SHALL apply the quoting rule of acceptance criterion 3 to the resulting field.
6. FOR ALL lists of 0 to 500 Check_Ins with names of 1 to 32 characters, parsing the output of the Csv_Exporter with an RFC 4180 reader SHALL return one record per Check_In plus the header, and the name field SHALL equal the original name, except for the single quote added by acceptance criterion 5 (round-trip property).
7. WHEN the list of Check_Ins is empty, THE Csv_Exporter SHALL return only the header line.
8. WHEN the host chooses the Download_Button, THE Spirit_Box_App SHALL save a file named `seance-<Session_ID>.csv` that holds the output of the Csv_Exporter for the Check_Ins from the latest Poll_Loop response, with a UTF-8 byte order mark at the start of the file.
9. IF no Poll_Loop response has been received when the host chooses the Download_Button, THEN THE Spirit_Box_App SHALL NOT save a file and SHALL show an error message stating that no attendance has been received yet.

### Requirement 5: Create a séance

**User Story:** As a host, I want to start a séance with a title, so that attendees see which event they are joining.

#### Acceptance Criteria

1. WHEN the Checkin_API receives `POST /api/seance` with a Title of 1 to 60 characters after trimming leading and trailing whitespace, THE Checkin_API SHALL create an Open_Seance, store it in the Seance_Store, and answer with status 201 and a body that holds the Session_ID, the trimmed Title and the Host_Secret.
2. THE Checkin_API SHALL generate the Session_ID and the Host_Secret from a cryptographically secure random source.
3. IF the Title is missing, is not a string, is empty after trimming, or is longer than 60 characters after trimming, THEN THE Checkin_API SHALL answer with status 400 and a message that says the Title must be 1 to 60 characters, and SHALL NOT store a Seance.
4. IF a generated Session_ID already exists in the Seance_Store, THEN THE Checkin_API SHALL generate a new Session_ID and repeat the check, up to 10 attempts.
5. IF 10 consecutive generated Session_IDs already exist in the Seance_Store, THEN THE Checkin_API SHALL answer with status 503 and a message that says a séance could not be created and the request can be retried, and SHALL NOT store a Seance.
6. IF the request body is not valid JSON, THEN THE Checkin_API SHALL answer with status 400 and a message that says the request was not understood, and SHALL NOT store a Seance.
7. THE Checkin_API SHALL store each Seance with an expiry of 24 hours from its creation time.
8. WHILE a Seance is 24 hours old or more, THE Checkin_API SHALL answer every request for that Session_ID with status 404.
9. THE Checkin_API SHALL create a Seance without requiring an account, an email address or any other identity.

### Requirement 6: Public view of a séance

**User Story:** As an attendee, I want to see the title of the séance before I join, so that I know I am in the right place.

#### Acceptance Criteria

1. WHEN the Checkin_API receives `GET /api/seance/:id/public` for a Session_ID that exists and is not expired, THE Checkin_API SHALL answer with status 200 and a body that holds the Title exactly as stored and a boolean `open` that is true for an Open_Seance and false for an Ended_Seance.
2. THE Checkin_API SHALL NOT include the Host_Secret, the Check_Ins or the Device_IDs in the body of the response to `GET /api/seance/:id/public`.
3. IF the Session_ID does not exist or is expired, THEN THE Checkin_API SHALL answer with status 404, a body that holds a message saying the séance was not found, and no Title, and THE Checkin_API SHALL leave all stored séance data unchanged.
4. IF the Session_ID in the request is not a well-formed Session_ID, THEN THE Checkin_API SHALL answer with the same status 404 and the same message as for a Session_ID that does not exist.
5. WHEN the Checkin_API answers any request, THE Checkin_API SHALL include the header `Cache-Control: no-store` in the response, including 200 and 404 responses.
6. WHEN the Checkin_API receives `GET /api/seance/:id/public`, THE Checkin_API SHALL NOT change the Check_Ins, the `open` value or the expiry time of the séance.

### Requirement 7: Host view of check-ins

**User Story:** As a host, I want to read the check-ins of my séance, so that the room display can light candles.

#### Acceptance Criteria

1. WHEN the Checkin_API receives `GET /api/seance/:id` with the Host_Secret of that Seance in the `Authorization` header, THE Checkin_API SHALL answer with status 200 and a body that holds the Title, the `open` boolean and the list of Check_Ins.
2. THE Checkin_API SHALL list each Check_In in the `GET /api/seance/:id` response with a name and a time, ordered by time from earliest to latest, and SHALL list Check_Ins with identical times in the order in which they were stored.
3. WHEN the Seance has no Check_Ins, THE Checkin_API SHALL answer `GET /api/seance/:id` with status 200 and an empty list of Check_Ins.
4. THE Checkin_API SHALL NOT include the Device_IDs or the Host_Secret in the body of the response to `GET /api/seance/:id`.
5. IF the `Authorization` header is missing, has no Host_Secret, or has a Host_Secret that differs from the stored one, THEN THE Checkin_API SHALL answer with status 404 and a body identical to the one for a missing Seance, and SHALL leave all stored data unchanged.
6. WHEN the Checkin_API compares the supplied Host_Secret with the stored Host_Secret, THE Checkin_API SHALL take the same amount of time regardless of the position of the first differing byte, so that response time does not reveal how many leading bytes matched.

### Requirement 8: Record a check-in

**User Story:** As an attendee, I want my check-in to count only when I really heard the screech, so that the attendance list is honest.

#### Acceptance Criteria

1. WHEN the Checkin_API receives `POST /api/seance/:id/checkin` for an Open_Seance with an Attendee_Name of 1 to 32 characters after trimming, a Device_ID of 32 lowercase hexadecimal characters, and a code that the Code_Verifier accepts for the current server time, and the Device_ID is not already in the Checkin_Log, THE Checkin_API SHALL add one Check_In with the trimmed name and the server time to the Checkin_Log, and SHALL answer with status 200 and a body that holds the name, the time and `alreadyCheckedIn` set to false.
2. WHEN the Checkin_API receives a check-in request for an existing Seance with a Device_ID that is already in that Seance's Checkin_Log, THE Checkin_API SHALL answer with status 200 and a body that holds the stored name, the stored time and `alreadyCheckedIn` set to true, SHALL NOT change the Checkin_Log, and SHALL NOT apply the name, code or Seance-ended checks of criteria 3, 4 and 5 to that request.
3. IF the Seance is an Ended_Seance and the Device_ID is not in its Checkin_Log, THEN THE Checkin_API SHALL answer with status 410 and a message that says the séance has ended, and SHALL NOT change the Checkin_Log.
4. IF the Seance is an Open_Seance, the Device_ID is not in the Checkin_Log, and the Code_Verifier does not accept the code for the current server time, THEN THE Checkin_API SHALL answer with status 403 and a message that says the code expired, and SHALL NOT change the Checkin_Log.
5. IF the Attendee_Name is missing, is empty after trimming, or is longer than 32 characters after trimming, THEN THE Checkin_API SHALL answer with status 400 and a message that says the name must be 1 to 32 characters, and SHALL NOT change the Checkin_Log.
6. IF the Device_ID is missing or is not exactly 32 lowercase hexadecimal characters, or the code is missing, THEN THE Checkin_API SHALL answer with status 400 and a message that names each field that is missing or malformed, and SHALL NOT change the Checkin_Log.
7. IF the Session_ID does not match any Seance, or the matching Seance is expired, THEN THE Checkin_API SHALL answer with status 404 and a message that says the séance was not found, and SHALL NOT change any Checkin_Log.
8. IF two or more requests with the same Device_ID for the same Seance arrive within the same processing window, THEN THE Checkin_API SHALL store exactly one Check_In for that Device_ID, and SHALL answer every request with status 200, where exactly one answer has `alreadyCheckedIn` set to false and all others have it set to true with the same stored name and time.
9. IF two or more requests with different Device_IDs for the same Seance arrive within the same processing window, THEN THE Checkin_API SHALL store one Check_In for each Device_ID, and SHALL answer each valid request with status 200.
10. THE Checkin_API SHALL read the time for the Code_Verifier and for the Check_In from the server clock, and SHALL ignore any time value supplied in the request.
11. THE Checkin_API SHALL return the stored name unchanged as a JSON string value with a JSON content type, and SHALL NOT render or interpret it as markup.

### Requirement 9: End a séance

**User Story:** As a host, I want to close the séance, so that nobody can check in after the event.

#### Acceptance Criteria

1. WHEN the Checkin_API receives `POST /api/seance/:id/end` for a Seance that is not ended and not expired, with the Host_Secret of that Seance in the `Authorization` header, THE Checkin_API SHALL mark the Seance as ended and answer with status 200 and a body that holds the number of Check_Ins, as an integer from 0 to the maximum number of Check_Ins allowed per Seance.
2. WHEN the Checkin_API receives `POST /api/seance/:id/end` for a Seance that is already ended, with the correct Host_Secret, THE Checkin_API SHALL answer with status 200, return the same Check_In count as the first call, and leave the Seance unchanged, including its ended state and its Check_Ins (idempotence).
3. IF the `Authorization` header is missing, is empty, or holds a Host_Secret that differs from the stored one, THEN THE Checkin_API SHALL answer with status 404, with the same status and body as for a missing Seance, and SHALL leave the Seance unchanged.
4. IF the Seance named by `:id` has expired or does not exist, THEN THE Checkin_API SHALL answer `POST /api/seance/:id/end` with status 404, with the same status and body as in criterion 3.
5. WHILE a Seance is ended and not expired, THE Checkin_API SHALL return all of its stored Check_Ins in the response to `GET /api/seance/:id`.
6. WHILE a Seance is ended, THE Checkin_API SHALL reject every new Check_In for that Seance, SHALL NOT add it to the stored Check_Ins, and SHALL answer with an error status that tells the sender the Seance is closed.

### Requirement 10: Host starts a séance

**User Story:** As a host, I want to start a séance from the Awaken and Speak screens, so that I can run check-in without any set-up.

#### Acceptance Criteria

1. THE Spirit_Box_App SHALL show the Seance_Control on the Awaken_Screen and on the Speak_Screen.
2. WHEN the host chooses the Seance_Control, THE Spirit_Box_App SHALL open the Host_Screen with the Start_Form within 300 ms.
3. THE Host_Screen SHALL NOT request microphone access, because the Screech_Loop only plays sound.
4. WHEN the host submits the Start_Form with a Title of 1 to 60 characters after trimming leading and trailing whitespace, THE Spirit_Box_App SHALL create or resume the AudioContext inside that tap handler, send `POST /api/seance`, and on success show the Room_Display.
5. IF the creation request receives no response within 10 seconds, THEN THE Start_Form SHALL keep the typed Title, show the message "No signal from the server. Check the network and try again.", and re-enable the Start button.
6. WHEN the creation succeeds, THE Spirit_Box_App SHALL keep the Session_ID, the Title and the Host_Secret in memory and in `sessionStorage`, and SHALL NOT write the Host_Secret to `localStorage`, a cookie, a URL or a log.
7. IF the Title is empty after trimming or longer than 60 characters, THEN THE Start_Form SHALL show a message that says the Title must be 1 to 60 characters, SHALL NOT send a request, and SHALL keep the typed Title.
8. IF the creation request fails because of no network, THEN THE Start_Form SHALL keep the typed Title, show the message "No signal from the server. Check the network and try again.", and re-enable the Start button.
9. IF the creation request fails with a server error, THEN THE Start_Form SHALL keep the typed Title, show the message "The server could not open a séance. Try again.", and re-enable the Start button.
10. WHEN the Host_Screen loads and `sessionStorage` holds a Session_ID, a Title and a Host_Secret, THE Spirit_Box_App SHALL resume that Seance, show the Room_Display, and restart the Screech_Loop and the Poll_Loop.
11. IF a resumed Seance answers 404 to the first poll, THEN THE Spirit_Box_App SHALL clear the stored Session_ID, Title and Host_Secret, stop the Screech_Loop and the Poll_Loop, and show the Start_Form with the message "That séance is gone. Start a new one."
12. THE Start_Form SHALL show in plain words that the host must keep this tab open and that closing it loses the host's control of the séance.
13. THE Start_Form SHALL have a text field and a Start button, each with a touch target of at least 44 px by 44 px.

### Requirement 11: Room display

**User Story:** As a host, I want a big display that shows who has arrived, so that the room sees the séance fill up.

#### Acceptance Criteria

1. WHILE a Seance is open, THE Room_Display SHALL show the Title.
2. WHILE a Seance is open, THE Room_Display SHALL show the Candle_Circle with one lit candle for each Check_In and the Attendee_Name under that candle, and unlit candles for the free places.
3. WHEN a poll response holds a Check_In that is not yet on the Candle_Circle, THE Room_Display SHALL light the next unlit candle and show the Attendee_Name under it within 500 ms of receiving the response.
4. THE Room_Display SHALL render every Attendee_Name as plain text, and SHALL NOT interpret it as markup.
5. WHEN a poll response is received, THE Room_Display SHALL show a Soul_Count equal to the number of Check_Ins in that response.
6. WHILE the Room_Display is open and the browser tab is visible, THE Poll_Loop SHALL send `GET /api/seance/:id` with the Host_Secret every 2 seconds, and SHALL NOT start a new request until the previous request has completed or timed out after 5 seconds.
7. WHEN the browser tab becomes visible after being hidden, THE Poll_Loop SHALL send a request within 500 ms.
8. IF a poll request fails because of no network or times out after 5 seconds, THEN THE Room_Display SHALL show the message "No signal from the server. Showing the last known list.", SHALL keep the Candle_Circle and the Soul_Count as they were, and THE Poll_Loop SHALL continue at the 2-second interval.
9. WHEN a poll request succeeds after a failed poll, THE Room_Display SHALL remove the no-signal message and update the Candle_Circle and the Soul_Count from the response.
10. WHERE the Check_In count is more than 100, THE Room_Display SHALL show the first 100 names, in the order of check-in, on the Candle_Circle and the remaining names in a vertically scrolling list below it.
11. WHILE the Exorcise_Toggle is on or the browser reports `prefers-reduced-motion: reduce`, THE Room_Display SHALL show lit candles with a still flame and SHALL NOT run the flicker or the light-up animation.
12. WHILE motion is allowed, THE Room_Display SHALL NOT flash more than 3 times in any 1-second period.
13. THE Room_Display SHALL use the colours and fonts of the ui-theme steering, with Creepster for the Title only, and SHALL give all text a contrast ratio of at least 4.5:1 against its background.
14. THE Room_Display SHALL give the Download_Button and the End_Hold a touch target of at least 44 px by 44 px.
15. THE Room_Display SHALL render without horizontal scrolling at viewport widths from 390 px in portrait up to a laptop window of 1440 px.

### Requirement 12: Host screech loop

**User Story:** As a host, I want the laptop to keep screeching, so that people who arrive late can still check in.

#### Acceptance Criteria

1. WHILE a Seance is open, THE Screech_Loop SHALL screech a Checkin_Packet through the existing transmit path of the Spirit_Box_App.
2. WHILE a Seance is open, THE Screech_Loop SHALL start each new screech 10 to 15 seconds (inclusive) after the start of the previous screech, with the delay chosen at random for each screech.
3. WHEN the Screech_Loop starts a screech, THE Screech_Loop SHALL build a new Checkin_Packet with the Rolling_Code of the Window that contains the current server-corrected time, computed in the browser with Web Crypto from the Host_Secret.
4. IF a previous screech is still playing when the next screech is due, THEN THE Screech_Loop SHALL delay the next screech until the previous screech ends, and SHALL then start it within 1 second of that end.
5. WHEN the host holds the End_Hold for the full hold time of the Hold_State_Machine, THE Spirit_Box_App SHALL send `POST /api/seance/:id/end` with the Host_Secret and SHALL stop the Screech_Loop within 1 second of the request succeeding.
6. WHEN the end request succeeds, THE Room_Display SHALL show the Title, the final Soul_Count, the text "The séance has ended" and the Download_Button, and SHALL stop the Poll_Loop within 1 second.
7. IF the end request fails because of no network, THEN THE Room_Display SHALL keep the Screech_Loop running, SHALL show the message "Could not close the séance. No signal from the server. Hold again to retry.", and SHALL keep the Seance open so that the host can hold the End_Hold again.
8. IF the end request fails for a reason other than no network, THEN THE Room_Display SHALL keep the Screech_Loop running and SHALL show an error message that states the request was rejected or failed and that the host can hold the End_Hold again.
9. WHILE a Seance is open, THE Spirit_Box_App SHALL request a screen wake lock where the browser supports it.
10. IF the browser releases the screen wake lock while a Seance is open, THEN THE Spirit_Box_App SHALL request it again when the Host_Screen becomes visible again.
11. IF the browser does not support the screen wake lock or denies the request, THEN THE Room_Display SHALL show a message that the laptop may sleep during the séance, and THE Screech_Loop SHALL keep running.
12. WHILE the Screech_Loop is running, THE Room_Display SHALL show the time until the next screech as a whole number of seconds, updated at least once per second, and SHALL show a screeching indicator while a screech is playing.
13. IF the browser blocks audio playback, THEN THE Room_Display SHALL show the message "The laptop is silent. Tap here to wake the sound.", with a tap target of at least 44 px by 44 px, and SHALL resume audio on the next tap.
14. WHEN the host leaves the Host_Screen without ending the Seance, THE Spirit_Box_App SHALL stop the Screech_Loop and the Poll_Loop within 1 second, and SHALL release the screen wake lock.
15. THE Spirit_Box_App SHALL run at most one Screech_Loop for each Host_Screen.

### Requirement 13: Attendee receives the checkin packet

**User Story:** As an attendee, I want my phone to offer me the séance when it hears it, so that I only need to tap Join.

#### Acceptance Criteria

1. WHEN the Listen_Screen decodes a Packet of type `checkin` and the Checkin_Parser returns Checkin_Fields, THE Spirit_Box_App SHALL stop capture, store the Session_ID and the code from the Checkin_Fields, and show the Join_Screen in place of the Reveal_Screen.
2. WHEN the Join_Screen opens, THE Spirit_Box_App SHALL send `GET /api/seance/:id/public` once, where `:id` is the Session_ID from the Checkin_Fields, and SHALL show the Title within 200 ms after a successful response arrives.
3. WHILE the public request is pending, THE Join_Screen SHALL show the text "Reaching the séance..." in place of the Title and SHALL show no Join_Button.
4. WHEN the public response arrives with `open` true, THE Join_Screen SHALL show the Title and an enabled Join_Button with a touch target of at least 44 px.
5. IF the public response says `open` is false, THEN THE Join_Screen SHALL show the Title, the message "The séance has ended. Nobody can join now." and no Join_Button.
6. IF the public request answers 404, THEN THE Join_Screen SHALL show the message "This séance was not found. It may be over." and no Join_Button.
7. IF the public request fails because of no network or does not complete within 10 seconds, THEN THE Join_Screen SHALL show the message "No signal from the server. Check the network." and a Retry button, and SHALL keep the stored Session_ID and code.
8. WHEN the user taps the Retry button, THE Join_Screen SHALL send the public request again and show the text "Reaching the séance..." until the response arrives.
9. WHEN the Listen_Screen decodes a Packet of type `checkin` that the Checkin_Parser rejects, THE Spirit_Box_App SHALL show the Reveal_Screen with the full decoded text, as in 13.6 of spec `spirit-box-app`.
10. WHEN the Listen_Screen decodes a Checkin_Packet again while the Join_Screen is open, THE Spirit_Box_App SHALL replace the stored code with the newest code and SHALL NOT open a second Join_Screen or send a second public request.
11. WHILE the Join_Screen or the Lit_Screen is open, THE Spirit_Box_App SHALL NOT play a UI_Sound.
12. WHEN a Checkin_Packet is decoded for the same Session_ID while the Lit_Screen is open, THE Spirit_Box_App SHALL ignore the Packet and leave the Lit_Screen unchanged.

### Requirement 14: Join the séance

**User Story:** As an attendee, I want to type my name once and tap Join, so that the host sees me in the room.

#### Acceptance Criteria

1. WHEN the Join_Screen opens, THE Name_Field SHALL show the name stored in `localStorage` from the last check-in, or an empty field when none is stored.
2. THE Name_Field SHALL accept a name of 1 to 32 characters, counted in Unicode code points after trimming leading and trailing whitespace, and SHALL show the remaining count (32 minus the current count) after each keystroke.
3. IF the Name_Field is empty after trimming or holds more than 32 characters, THEN THE Join_Button SHALL be disabled and THE Join_Screen SHALL show a message in plain words that the name must be 1 to 32 characters.
4. WHEN the attendee chooses the Join_Button, THE Spirit_Box_App SHALL send `POST /api/seance/:id/checkin` with the Session_ID, the code from the latest decoded Checkin_Packet, the trimmed name and the Device_ID.
5. WHEN the Spirit_Box_App needs a Device_ID and none is in `localStorage`, THE Spirit_Box_App SHALL create 16 random bytes with Web Crypto, store them as 32 lowercase hexadecimal characters and reuse the stored value for all later check-ins.
6. WHEN the check-in request succeeds, THE Spirit_Box_App SHALL save the name returned by the server in `localStorage` and show the Lit_Screen.
7. WHILE the check-in request is pending, THE Join_Button SHALL be disabled and show the text "Joining...", so that one tap sends one request.
8. IF the check-in request fails (network error, no response within 10 seconds, or a non-success response), THEN THE Spirit_Box_App SHALL stay on the Join_Screen, keep the typed name in the Name_Field, re-enable the Join_Button, show an error message in plain words that says what happened, and show a Retry button that sends the same request again.
9. THE Join_Screen SHALL render the Title and the name as plain text, with no HTML interpretation of their content.
10. THE Name_Field, the Join_Button, the Retry button and the Leave button SHALL each have a touch target of at least 44 px by 44 px.
11. THE Join_Screen SHALL render without horizontal scrolling at 390 px wide in portrait, and SHALL give every text a contrast of at least 4.5:1.
12. WHEN the attendee chooses a Leave button on the Join_Screen, THE Spirit_Box_App SHALL return to the Listen_Screen without sending a check-in request.

### Requirement 15: Lit screen and repeat check-in

**User Story:** As an attendee, I want to see that I am counted, so that I know I can put my phone away.

#### Acceptance Criteria

1. WHEN the check-in succeeds, THE Lit_Screen SHALL show the text "Your candle is lit", the name stored by the server, and the Title, within 500 ms of the success response being received.
2. WHEN the check-in succeeds and `alreadyCheckedIn` is false, THE Lit_Screen SHALL run the Candle_Animation exactly once, with a total duration of at most 3 seconds, and SHALL then keep the candle lit and still.
3. WHEN the check-in succeeds and `alreadyCheckedIn` is true, THE Lit_Screen SHALL show the text "Your candle is lit", the stored name, the Title, and the note "You were already counted.", and SHALL NOT run the Candle_Animation.
4. WHILE the Exorcise_Toggle is on or the browser reports `prefers-reduced-motion: reduce`, THE Lit_Screen SHALL show a lit candle with a still flame and SHALL NOT run the Candle_Animation.
5. WHILE motion is allowed, THE Candle_Animation SHALL NOT flash more than 3 times in any 1-second period.
6. THE Lit_Screen SHALL NOT contain any control that sends a check-in request.
7. WHEN the user taps the "Back to listening" button, THE Lit_Screen SHALL return to the Listen_Screen.
8. THE Lit_Screen SHALL render the "Back to listening" button with a touch target of at least 44 px by 44 px.
9. THE Lit_Screen SHALL render the candle and all text in phosphor green or bone white with a text contrast ratio of at least 4.5:1 against the background, and SHALL NOT use a red colour on this screen.

### Requirement 16: Plain-word check-in errors

**User Story:** As an attendee, I want to know what went wrong, so that I can fix it or stop trying.

#### Acceptance Criteria

1. IF the check-in request answers 403 because the code expired, THEN THE Join_Screen SHALL show the message "The code expired. Move closer and listen again." and a button "Listen again" that is at least 44 px high and wide, and THE Join_Screen SHALL keep the typed name.
2. WHEN the attendee taps the "Listen again" button, THE Spirit_Box_App SHALL return to the Listen_Screen and start capture within 1 second, with the typed name preserved.
3. IF the check-in request answers 410, THEN THE Join_Screen SHALL show the message "The séance has ended. Nobody can join now." and no Join_Button.
4. IF the check-in request answers 404, THEN THE Join_Screen SHALL show the message "This séance was not found. It may be over." and no Join_Button.
5. IF the check-in request answers 400 for the name, THEN THE Join_Screen SHALL show the message "The name must be 1 to 32 characters.", keep the typed name unchanged, and re-enable the Join_Button.
6. IF the check-in request fails because no response is received (no network, or no response within 10 seconds), THEN THE Join_Screen SHALL keep the typed name, show the message "No signal from the server. Check the network and tap Join again." and re-enable the Join_Button.
7. IF the check-in request answers with a status of 500 to 599, THEN THE Join_Screen SHALL keep the typed name, show the message "The server could not count you. Tap Join to try again." and re-enable the Join_Button.
8. IF the check-in request answers with any status not covered by criteria 1 to 7 and not in 200 to 299, THEN THE Join_Screen SHALL keep the typed name, show a message in plain words saying the check-in failed and that the attendee can tap Join to try again, and re-enable the Join_Button.
9. THE Join_Screen SHALL show every error message in red text with a contrast ratio of at least 4.5:1 against its background, and SHALL NOT show an HTTP status code, an exception name or a stack trace in any error message.
10. WHEN the attendee taps the Join_Button after a failed attempt, THE Spirit_Box_App SHALL send one new check-in request using the most recently stored code and the current name, and SHALL clear the previous error message before the request is sent.

### Requirement 17: Server storage and concurrency

**User Story:** As a host, I want the server to keep my séance for the day without extra set-up, so that I can run the event on a free tier.

#### Acceptance Criteria

1. THE Checkin_API SHALL be written in TypeScript as Netlify Functions that are served under `/api` on the same origin as the Spirit_Box_App.
2. WHEN a Seance is created or a Check_In is accepted, THE Checkin_API SHALL store the Seance or the Check_In in the Seance_Store before it sends a success response.
3. WHEN a Check_In is accepted, THE Checkin_API SHALL store it under its own key made from the Session_ID and the Device_ID, and SHALL write it only if that key does not already exist.
4. IF two check-ins from different devices for the same Seance arrive at the same time, THEN THE Checkin_API SHALL keep both Check_Ins, and neither SHALL overwrite the other.
5. IF a check-in arrives for a key that already exists, THEN THE Checkin_API SHALL leave the stored Check_In unchanged and answer as in criterion 2 of Requirement 8, with status 200 and `alreadyCheckedIn` set to true.
6. WHEN a Seance is 24 hours old or more, THE Checkin_API SHALL treat the Seance and its Check_Ins as missing in every response, and SHALL delete their records within 1 hour of that age being reached.
7. THE Checkin_API SHALL read the Core pure functions from `@screech/core` for the Code_Verifier, the Checkin_Log rules, the name rules and the Csv_Exporter, and SHALL NOT duplicate that logic.
8. THE Checkin_API SHALL answer every response in JSON with `Content-Type: application/json`, except for a response with no body.
9. THE Checkin_API SHALL NOT write the Host_Secret, a Rolling_Code or a Device_ID to a log.
10. IF an unexpected error occurs in a function, THEN THE Checkin_API SHALL answer with status 500 and a JSON message that does not hold a stack trace or a stored value, and SHALL leave previously stored Seances and Check_Ins unchanged.
11. IF a request uses a method that the endpoint does not support, THEN THE Checkin_API SHALL answer with status 405 and an `Allow` header that lists the supported methods.

### Requirement 18: Local development and delivery

**User Story:** As a developer, I want the functions and the app to run on one origin locally, so that the host and attendee flows work without extra set-up.

#### Acceptance Criteria

1. THE repository SHALL hold a `netlify.toml` at the repository root that builds `apps/web`, publishes the build output of `apps/web`, sets `apps/checkin-api` as the functions location and maps every path beginning with `/api/` to those functions.
2. WHEN a developer runs `netlify dev` from the repository root, THE Spirit_Box_App and the Checkin_API SHALL be served from one origin (same scheme, host and port), so that a request from the Spirit_Box_App to a relative URL beginning with `/api/` reaches the Checkin_API and returns a response from it.
3. THE Spirit_Box_App SHALL issue every Checkin_API request with a relative URL beginning with `/api/` and SHALL contain zero hard-coded host names, schemes or port numbers in Checkin_API request URLs.
4. THE `apps/checkin-api/README.md` SHALL describe each Checkin_API endpoint (its method, path, inputs and outputs), each kind of data held in the Seance_Store, the command to run `netlify dev`, and the command to run the tests.
5. WHEN `pnpm test` runs from the repository root, THE test run SHALL execute at least one fast-check property test and at least one unit test for each of the Checkin_Builder, the Checkin_Parser, the Code_Function, the Code_Verifier, the Checkin_Log and the Csv_Exporter, and SHALL exit with a non-zero status IF any of them fails.
6. WHEN `pnpm test` runs from the repository root, THE test run SHALL execute tests of every Checkin_API handler that use an in-memory replacement for the Seance_Store, and those tests SHALL complete with zero network calls and zero reads or writes to the real Seance_Store.
7. IF `netlify dev` cannot serve the Checkin_API (for example, the functions fail to build), THEN THE README at `apps/checkin-api/README.md` SHALL list the diagnostic step a developer takes to find the cause, so that the developer can tell a functions failure from a Spirit_Box_App failure.

### Requirement 19: Security and privacy

**User Story:** As a host and as an attendee, I want the tool to hold as little personal data as possible, so that using it is low-risk.

#### Acceptance Criteria

1. WHEN the Checkin_API records a Check_In, THE Checkin_API SHALL store only the Attendee_Name, the Device_ID and the Check_In time, and SHALL store no other field from the request, including IP address and user-agent string.
2. WHEN the Checkin_API creates a Seance, THE Checkin_API SHALL store only the Session_ID, the Title, the Host_Secret, the creation time and the ended flag, and SHALL store no other field from the request.
3. THE Checkin_API SHALL NOT send a Set-Cookie header in any response, including error responses.
4. THE Spirit_Box_App SHALL render each Title and each Attendee_Name as React text nodes, so that a value containing the characters `<script>alert(1)</script>` appears on screen as literal text and runs no script. THE Spirit_Box_App SHALL NOT use `dangerouslySetInnerHTML` or `innerHTML` for these values.
5. THE Spirit_Box_App SHALL keep the Host_Secret only in memory and in `sessionStorage`, and SHALL NOT write the Host_Secret to `localStorage`, cookies, URLs or logs.
6. WHEN an attendee checks in, THE Spirit_Box_App SHALL keep only the Device_ID and the last Attendee_Name in `localStorage`, and SHALL write no other key from the attendee side to `localStorage`.
7. IF a request body is larger than 2 KB (2,048 bytes), THEN THE Checkin_API SHALL answer with status 413, SHALL NOT read or write the Seance_Store for that request, and SHALL leave stored data unchanged.
8. IF any field of a request is missing, has the wrong type, or exceeds its length limit, THEN THE Checkin_API SHALL reject the request with a 4xx status and an error body that names the invalid field, before any read or write of the Seance_Store, and SHALL leave stored data unchanged.
9. WHEN the Checkin_API receives a valid request, THE Checkin_API SHALL complete field validation before its first read or write of the Seance_Store.
